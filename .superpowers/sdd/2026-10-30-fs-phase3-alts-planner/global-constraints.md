## Global Constraints

- Retail only, Midnight 12.x; Lua 5.1 semantics. Every addon file begins `local ADDON_NAME, ns = ...`.
- Modules: `local M = ns.FS:NewModule("<Name>", "AceEvent-3.0")`; access others only via `ns.FS:GetModule("<Name>")` public functions and bus messages. No module reads another module's private tables (the spec §4.3 DB layout is public; phase-3-owned keys are listed under Contract additions below).
- Money is integer copper; time is server seconds from `ns.FS:Now()`. Every stored record that can go stale has a `time` field.
- `Modules/PlanCalc.lua` references no WoW globals and no `ns.FS` (same rule as `ns.Math`).
- Design rule 1: Characters/Planner tabs work on any character from saved data; no profession window needed.
- Design rule 2/7: never replace, hide, reparent or write fields of Blizzard frames; post-hooks only. Phase 3 adds no protected calls.
- Design rule 6: stale character data, missing knowledge data, unknown concentration and missing prices are shown, never hidden or shown as 0.
- Event handlers and UI hooks run through `ns.FS:SafeCall(moduleName, fn, ...)`; bursty events go through `ns.FS:Debounce(key, seconds, ns.FS:Wrap(moduleName, fn))` (1a's `Debounce` does not isolate errors, so the fn is always `Wrap`ped).
- Messages use 1a's `ns.Msg` constants (`ns.Msg.ALTS_CHANGED` = `"FS_ALTS_CHANGED"`, `ns.Msg.DATA_CHANGED`, `ns.Msg.RECIPES_CHANGED`); the literal names are used in tests.
- Tab ids/orders: `characters` = 70, `planner` = 80 (lowercase ids, 1a). UI uses own frames + Blizzard templates, no AceGUI. Message-driven redraws call 1a's `MainWindow:RefreshTab(id)` (no-op unless that tab is selected and shown).
- GameData files follow 1a's format (1a Task 5): header comment `-- GENERATED by tools/gamedata/gen_phase3.lua from wago.tools DB2 CSV, build <version>.<build>. Do not edit.`, then `local ADDON_NAME, ns = ...`, then `ns.GameData.Define("<Name>", <integer build>|nil, <table>)`. Runtime code reads them only via `ns.GameData.Get("Knowledge")` / `Get("RecipeSources")`; the build comes from `ns.GameData.Build()` / `Status()`. Generator code reuses 1a's `tools/lib/csv.lua` and `tools/lib/serialize.lua` and its cache dir `tools/gamedata/cache/<version.build>/`.
- TOC placement (1a convention): Data files after `Data\GameData_Manual.lua` (before the Math files); modules after `Modules\Diagnostics.lua` and the 1b/2 modules; tab and view files between `UI\MainWindow.lua` and `UI\Tabs\Settings.lua`; `UI\AltsTooltips.lua`, `UI\AltsDashboard.lua` after `UI\Tooltips.lua`. 1a's TOC test fails on a listed file that does not exist, so each task adds its files when it creates them.
- Settings live in `db.global.settings.alts` / `settings.planner`, created lazily with defaults (as 1b does for `settings.crafting`); `db.global.recipeCatalog` is created lazily. No migration needed. `Alts` and `Planner` are ordinary (non-core) modules, so 1a's `"modules"` options group lists a toggle for each.
- Globals not in 1a's `.luacheckrc` `stds.wow.read_globals` are added by the task that first reads them (1b's rule): `C_QuestLog`, `C_DateAndTime`, `GetCurrentRegion`, `canaccessvalue` (Task 6/7), `C_Spell` if 1b has not added it (Task 6), `RAID_CLASS_COLORS`, `CreateScrollBoxListLinearView`, `CreateDataProvider`, `ScrollUtil` (Task 12/13). Test helper globals (`phase3_env`, `NOW`, `WS`) go into the `tests/` std.
- Tests: `busted` from repo root; lint `luacheck .` must stay clean. Commits: conventional (`feat:`, `test:`, `chore:`, `fix:`).

## Rules carried from phases 1a-2 (binding)

- Design rule 7 in detail: allowed are `hooksecurefunc`, `frame:HookScript`, EventRegistry callbacks, reading Blizzard fields, and anchoring OWN frames to Blizzard frames. Not allowed: assigning any field on a Blizzard frame/table, `SetScript` on a Blizzard frame, calling Blizzard mixin methods that change state. Phase 3 adds no protected calls; the existing structural tests (ClaimBest / CraftRecipe click-only) must stay green.
- Design rule 6: unknown money/values are `nil`, never `0`; UI shows "--"/"?"/"no data"; ages via `ns.UI.FormatAge`, money via `ns.UI.FormatMoney` (and `ns.UI.OrdersPanel.CompactMoney` in narrow cells, full value in the tooltip).
- Never write saved data while `ns.FS.dbIsNewer` (settings: use `ns.Util.SettingsAccessor` like Orders/Ledger/OrderAlert; other writes: a `writable()` guard). Add a dbIsNewer spec for every new writer.
- Event/message handlers: `ns.FS:Wrap("<Module>", fn)`; core modules use a log-only source name (e.g. "Queue:OrderFulfilled") so an error does not disable the core module. Register events only while needed; OnDisable unregisters and cancels every Debounce/ticker; no leaked registrations.
- Other modules looked up at call time with `ns.FS:GetModule(name, true)`, never cached at file load.
- UI layout lessons from phase 2 (Tasks 10-12 failed these first time): the main window's MINIMUM content width is 516 px (MainWindow 700 − 12 − 150 − 10 − 12); every table's flexible column keeps ≥ 120 px there; lower-priority columns hide below that (recompute in OnSizeChanged); anchor columns from both edges when the flexible column isn't first; anything truncated goes into the row tooltip; status/notice lines lead with the key word and have a tooltip. Add anchor/width specs at 516 px (shared fake font strings record SetPoint/SetWidth). Overflowing chips/lists need a "+N" affordance, never silent hiding.
- Interface contract (`docs/superpowers/plans/2026-10-30-fs-interface-contract.md`) is current through phase 2; each phase-3 task that adds a contract item from the plan's "Contract additions" updates the contract in the same task.
